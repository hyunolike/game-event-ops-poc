# 4단계 — 부하 테스트

**질문**: Redis Lua 로 재고를 차감하는 것이 DB 트랜잭션으로 차감하는 것보다 실제로 얼마나 나은가.

**답**: 같은 조건에서 **처리량 22~44배, p99 응답시간 1/25~1/29**.
그리고 두 방식 모두 **초과 발급은 0건**이다 — 정확성을 포기해서 얻은 속도가 아니다.

---

## 측정 환경과 한계 (먼저 밝힘)

| 항목 | 값 |
|---|---|
| CPU / RAM | 4 core (Intel Xeon @ 2.80GHz) / 15 GB |
| 애플리케이션 | .NET 8, **Release 빌드**, 단일 인스턴스 |
| MSSQL | SQL Server 2022 CU26, 컨테이너, 메모리 4GB, **데이터 파일은 호스트 파일시스템** |
| Redis | 7.0.15, 컨테이너 |
| 부하 생성기 | k6 v0.54.0 |

**한계를 분명히 해 둔다.**

1. **부하 생성기가 대상과 같은 장비에서 돈다.** k6·앱·MSSQL·Redis 가 4코어를 나눠 쓴다.
   따라서 아래 숫자는 **이 시스템의 절대 용량이 아니다.** 의미가 있는 것은 **같은 조건에서의 상대 비교**다.
2. 원 요구사항의 **10,000 VU 스파이크는 이 장비에서 의미가 없다.** 그 규모에서는 부하 생성기 자체가
   병목이 되어 대상이 아니라 k6 를 측정하게 된다. 대신 **200 / 1,000 / 3,000 VU** 세 지점을 측정해
   "VU 가 늘 때 각 방식이 어떻게 변하는가" 를 본다. 이 기울기가 단일 지점의 절대값보다 많은 것을 말해 준다.
3. MSSQL 데이터 파일은 컨테이너 레이어(vfs)가 아니라 **호스트 파일시스템에 바인드 마운트**했다.
   vfs 의 I/O 오버헤드가 DB 쪽 수치를 부당하게 나쁘게 만들지 않도록 한 조치다.

## 비교 대상 세 가지

셋 다 **같은 규칙**(기간·중단·유저당 한도·멱등)을 강제하고 **같은 `IssuanceLogs` 스키마**에 기록한다.
다른 것은 재고를 어디서 어떻게 차감하는가뿐이다.

| 경로 | 엔드포인트 | 방식 |
|---|---|---|
| **Redis Lua** | `POST …/coupons/issue` | Lua 스크립트에서 원자적으로 차감. DB 적재는 비동기 |
| **DB 이벤트행 락** | `POST …/coupons/issue-db` | 이벤트 행에 `UPDLOCK` → 발급 전체가 직렬화. Redis 없이 정확성을 얻는 가장 흔한 구현 |
| **DB READPAST** | `POST …/coupons/issue-db-skiplocked` | 이벤트 행을 잠그지 않고 미발급 쿠폰 행을 `READPAST` 로 집어옴. 잠긴 행은 건너뛴다 |

세 번째를 넣은 이유는 **"DB 를 일부러 못 만든 것 아니냐"** 는 반론을 미리 닫기 위해서다.
DB 만으로 할 수 있는 최선에 가까운 구현을 함께 측정한다.

> **전제 검증**: 빠르지만 초과 발급하는 구현과 비교하면 수치가 아무것도 증명하지 못한다.
> 그래서 세 경로 모두에 대해 "초과 발급 0건 · 유저 한도 준수 · 멱등 처리 · 중단 반영" 을
> 통합 테스트로 먼저 단언한다 (`DbIssueCorrectnessTests`, 11건).

## 시나리오 1 — 스파이크 (처리량 · 응답시간)

이벤트 오픈 직후를 재현한다. **0 → 정점 VU 10초 램프 → 20초 유지 → 5초 램프다운.**
요청의 **20%는 좁은 유저 풀에서 반복**해 "안 됐다고 생각하고 계속 누르는" 실제 패턴을 섞는다.
재고는 측정 구간 내내 소진되지 않도록 넉넉히 둔다 — 소진 후에는 값싼 거부 경로만 측정하게 되기 때문이다.

**매 실행 전 DB·Redis 를 비우고 앱을 재기동한다.** 앞선 실행이 남긴 수십만 행이
인덱스 크기와 버퍼풀 상태를 바꿔 놓으면 나중에 실행된 경로가 부당하게 불리해진다.

### 결과

| 경로 | VU | 처리량 (req/s) | p50 | p95 | p99 | max | 발급 성공 | 시스템 오류 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| **Redis Lua** | 200 | **8,912** | **14 ms** | **37 ms** | **64 ms** | 126 ms | 249,582 | 0 |
| DB 이벤트행 락 | 200 | 223 | 779 ms | 1,008 ms | 1,552 ms | 3,725 ms | 6,281 | 0 |
| DB READPAST | 200 | 395 | 328 ms | 860 ms | 2,246 ms | 10,603 ms | 11,134 | 0 |
| **Redis Lua** | 1,000 | **8,908** | **48 ms** | **127 ms** | **191 ms** | 403 ms | 249,671 | 0 |
| DB 이벤트행 락 | 1,000 | 201 | 4,473 ms | 5,517 ms | 6,384 ms | 25,619 ms | 6,162 | 0 |
| DB READPAST | 1,000 | 394 | 2,002 ms | 2,826 ms | 7,970 ms | 28,239 ms | 11,235 | 1 |
| **Redis Lua** | 3,000 | **8,495** | **145 ms** | **391 ms** | **551 ms** | 887 ms | 237,676 | 0 |
| DB 이벤트행 락 | 3,000 | 202 | 12,069 ms | 15,156 ms | 15,804 ms | 34,292 ms | 7,249 | 4 |
| DB READPAST | 3,000 | 322 | 6,605 ms | 10,914 ms | 14,596 ms | 22,531 ms | 10,368 | 2 |

### 배수

| VU | Redis vs 이벤트행 락 | Redis vs READPAST |
|---:|---:|---:|
| 200 | **39.9배** | 22.6배 |
| 1,000 | **44.3배** | 22.6배 |
| 3,000 | **42.1배** | 26.4배 |

### 숫자가 말하는 것

**처리량의 기울기가 전부 다르다.**

- **DB 두 방식은 VU 를 15배 늘려도 처리량이 그대로다** (223 → 202, 395 → 322).
  늘어난 것은 대기 시간뿐이다. p50 이 779ms → 12,069ms 로 **15배** 늘었다.
  이것이 직렬화의 정의다 — 더 많이 몰려와도 초당 처리량은 변하지 않고 줄만 길어진다.
- **Redis 는 VU 15배에도 처리량이 8,912 → 8,495 로 유지된다.** p50 은 14ms → 145ms 로 늘었지만
  이는 큐잉이 아니라 4코어를 나눠 쓰는 포화 상태의 자연스러운 결과다.
- **꼬리 지연의 차이가 더 크다.** 3,000 VU 에서 p99 는 551ms 대 15,804ms — **29배**다.
  평균은 감출 수 있어도 꼬리는 못 감춘다. 이벤트 오픈 때 화내는 사람은 p99 쪽에 있다.
- DB 경로의 `max` 가 25~34초인 것은 명령 타임아웃(30초)에 근접한 요청들이다.
  3,000 VU 에서 시스템 오류가 4건 나온 것은 그 경계를 넘은 것이다.

## 시나리오 2 — 소진 정확성

재고 **10,000**, 300 VU, 20% 중복 요청. **발급 수가 설정 수량과 정확히 일치하는가**를 본다.

| 경로 | 발급 성공 | 수량 소진 거부 | 한도 초과 | 시스템 오류 | 처리량 | DB 적재 이력 |
|---|---:|---:|---:|---:|---:|---:|
| Redis Lua | **10,000** | 191,697 | 50,260 | 0 | 8,398/s | 10,000 |
| DB 이벤트행 락 | **10,000** | 5,528 | 3,873 | 0 | 185/s | — |
| DB READPAST | **10,000** | 18,589 | 7,097 | 2 | 340/s | 10,000 |

**셋 다 정확히 10,000건.** 초과도 미달도 없다.

Redis 경로는 총 **251,957건**의 요청을 처리하면서 그중 정확히 10,000건만 발급했다.
비동기 적재 후 DB 이력도 10,000건으로 일치한다 — Redis(원천)와 DB(영속화)가 어긋나지 않는다.

> 시나리오 2 에서 Redis 경로의 거부 건수가 훨씬 많은 것은 처리량이 높아 같은 시간에
> 더 많은 요청을 소화했기 때문이다. 소진은 약 2초 만에 끝나고 나머지 시간은 전부 거부 처리였다.

## 개선 전후 — 인덱스 하나가 40배를 만든 이야기

비교군을 처음 구현했을 때 DB 경로는 **200 VU 에서 5.6 req/s** 였고, 요청의 **94%가 타임아웃**이었다.
그대로 리포트에 실었다면 "Redis 가 1,500배 빠르다" 는 말도 안 되는 결론이 나왔을 것이다.

실행 계획을 떠보니 원인이 나왔다.

```
|--Index Scan(OBJECT:[IssuanceLogs].[IX_IssuanceLogs_EventId_RequestedAt],
              WHERE: EventId=(2) AND Result=(1) AND UserId=N'hot-1')
```

유저별 발급 횟수를 세는 질의가 **인덱스 스캔**이었다. 이 질의에는 `UPDLOCK, HOLDLOCK` 이 붙어 있다 —
유저 한도를 강제하려면 동시 삽입을 막아야 하기 때문이다. 결과적으로 **모든 트랜잭션이
258,000행 인덱스 전체에 범위 잠금**을 걸고 있었다.

```csharp
// 성공 행만 담으므로 실패가 많아져도 커지지 않는다.
e.HasIndex(x => new { x.EventId, x.UserId })
 .HasDatabaseName("IX_IssuanceLogs_EventId_UserId_Issued")
 .HasFilter("[Result] = 1");
```

| DB 이벤트행 락 · 200 VU | 처리량 | 시스템 오류 |
|---|---:|---:|
| 인덱스 추가 전 | 5.6 req/s | 182 / 194 (94%) |
| 인덱스 추가 후 | **223 req/s** | 0 |

**40배.** 방식을 바꾼 게 아니라 인덱스 하나를 추가했을 뿐이다.

이 경험이 리포트에 남을 가치가 있다고 본다. **비교 대상을 제대로 만들지 않으면 비교는 자기 확인에 불과하다.**
지금의 22~44배는 "Redis 가 잘 만든 DB 구현보다 빠르다" 는 뜻이고, 처음의 1,500배는
"내가 DB 를 잘못 썼다" 는 뜻이었다.

## 왜 이런 차이가 나는가

수치가 아니라 구조의 차이다.

| | Redis Lua | DB 트랜잭션 |
|---|---|---|
| 차감 단위 | 인메모리 정수 연산 1회 | 트랜잭션 시작 → 잠금 → I/O → 커밋 |
| 직렬화 범위 | Redis 단일 스레드가 스크립트 단위로 (수 µs) | 잠금 보유 시간 전체 (수 ms) |
| 커넥션 | 발급 중 DB 커넥션 **0개** | 요청당 1개를 **트랜잭션 내내 점유** |
| 디스크 | 없음 | 로그 기록 + 커밋 |
| 응답까지 필요한 작업 | 재고 차감만 | 재고 차감 + 이력 INSERT |

**커넥션 점유가 특히 크다.** 초기 측정에서 DB 경로는 커넥션 풀(기본 100)을 고갈시켜
500 에러를 냈다. 잠금 대기가 길어지면 커넥션이 그만큼 오래 묶이고, 풀이 잠금보다 먼저 바닥난다.
측정에서는 풀을 200으로 늘려 **잠금 동작 자체를 재도록** 했고, 고갈 시에는 503 으로
우아하게 거부하도록 고쳤다(`detail: "connection-pool-exhausted"`).

Redis 경로는 발급 중 DB 커넥션을 하나도 쓰지 않는다. DB 는 나중에 배치로 따라온다.

## 알려진 차이 하나

DB 비교 경로는 **Redis 를 전혀 건드리지 않는다.** 그래서 이 경로로 발급하면 운영툴의
"잔여 수량"(Redis 기준)이 줄지 않는다 — 실제로 시나리오 2 의 DB 실행 후 현황 API 는
`remaining: 10000, issued: 0, persistedLogs: 10000` 을 보고했다.

이는 버그가 아니라 **비교군의 성격**이다. 두 원천을 동기화하면 그 비용이 측정에 섞여
비교가 흐려진다. DB 경로는 측정 전용이며 운영 경로가 아니다.

따라서 **한 이벤트에 두 경로를 섞어 쓰면 안 된다.** Redis 가 풀에서 꺼내 갔지만 아직
DB 에 반영되지 않은 쿠폰은 `Status = 0` 이므로, 그 틈에 DB 경로가 같은 쿠폰을 다시 집어간다.
측정은 항상 경로별로 별도 이벤트를 만들어 수행한다.

## 측정하며 겪은 함정 (재현하려는 사람을 위해)

1. **`ss -ltnp` 가 이 컨테이너에서 아무 출력도 내지 않는다.** 포트로 프로세스를 찾아 죽이는
   초기화 로직이 조용히 실패했고, **낡은 앱 인스턴스가 계속 트래픽을 받고 있었다.**
   그 상태의 수치는 전부 버렸다. 지금은 프로세스 이름으로 종료하고 포트가 실제로 응답을
   멈출 때까지 기다린다.
2. **`set -euo pipefail` + `grep` 조합.** `pids=$(... | grep ...)` 에서 grep 이 아무것도 못 찾으면
   명령 치환이 실패해 스크립트가 통째로 죽는다. 조용히 죽어서 원인을 찾는 데 시간이 걸렸다.
3. **바인드 마운트에 남은 DB 파일.** 컨테이너를 다시 만들면 master 는 DB 를 모르는데
   `.mdf` 파일은 남아 있어 `CREATE DATABASE` 가 실패한다.

## 룰렛 추첨 경로 — 측정 하네스 (수치 미측정)

쿠폰 발급과 증명하려는 성질이 다르다.

| | 쿠폰 발급 | 룰렛 추첨 |
|---|---|---|
| 정확성 | "정확히 N개" — 단일 카운터 | **"한정 경품이 재고를 넘지 않는다"** — 경품별 카운터 |
| 부가 성질 | 없음 | **분포가 가중치와 같다**, 소진 뒤 대체 치환이 새지 않는다 |
| 스크립트 비용 | 키 7개 | 키 9개 + 누적 가중치 스캔 |

마지막 줄 때문에 **룰렛이 쿠폰보다 느린 것이 정상이다.** 얼마나 느린지가 의미 있는 수치이고,
그 대가로 얻는 것이 위의 두 성질이다.

### 하네스

| 파일 | 역할 |
|---|---|
| `loadtest/draw-spike.js` | k6 스파이크 시나리오. 결과별 + **슬롯별** 카운터, 대체 치환·천장 적용 수 |
| `loadtest/provision-draw.sh` | 운영툴 폼으로 룰렛 생성. 시뮬레이션 게이트를 그대로 거친다 |
| `loadtest/run-draw.sh` | VU 3단계 측정 + **매 실행 뒤 초과 지급 0건 확인** |

```bash
docker compose up -d --wait
STOCK=5000 bash loadtest/run-draw.sh /tmp/draw-results
```

### 이 하네스가 실제로 확인하는 것

처리량 숫자만 남기면 이 측정은 의미가 없다. `run-draw.sh` 는 매 실행이 끝난 뒤
운영툴의 현황 API 에 직접 물어 **한정 경품 당첨 수가 재고를 넘지 않았는지**를 확인하고,
넘었으면 0이 아닌 종료 코드로 끝난다. 측정이 곧 검증이다.

k6 쪽에서도 몇 가지를 구분해 센다.

- **멱등 재생은 슬롯 카운터에서 뺀다.** 포함시키면 같은 당첨이 두 번 세어져
  "재고보다 많이 당첨됐다" 는 거짓 결론이 나온다.
- **대체 치환 수를 따로 센다.** `슬롯0 당첨 + 대체 치환 = 슬롯0 을 뽑은 총횟수` 가 성립해야
  소진 경계에서 새는 요청이 없다는 뜻이다.
- **재시도는 같은 `requestId` 로 보낸다.** 새 난수로 한 번 더 보내는 것은 재시도가 아니라
  재추첨이고, 그러면 멱등 경로를 전혀 밟지 못한다.

### 수치

추정치를 적어 두면 비교표 전체의 신뢰가 무너진다.
