# AI 활용 기록

이 저장소의 코드는 **Claude Code(AI)와의 협업으로 작성됐다.** 숨길 이유가 없고,
숨기면 "어디까지 검증됐는가" 라는 더 중요한 질문에 답할 수 없다.

이 문서는 세 가지를 남긴다 — **역할 분담**, **AI 가 만든 코드에서 실제로 나온 결함**,
**효과가 있었던 프롬프트 패턴**.

---

## 역할 분담

| | 사람 | AI |
|---|---|---|
| 요구사항 정의 | 6단계 작업 명세를 직접 작성 | — |
| 설계 | 설계안 검토·승인 | ERD·엔티티·인덱스 설계안 작성, 트레이드오프 비교 |
| 구현 | — | 전 영역 |
| 테스트 | — | 통합 테스트 46건 작성·실행 |
| 부하 측정 | 측정 항목 지정("개선 전후 비교") | 시나리오 작성·실행·리포트 |
| 진행 통제 | 단계마다 승인, 환경 선택지 결정 | 각 단계 완료 시 정지 후 보고 |
| 검증 요구 | "실행 가능한 명령어와 함께 제시하라" | 매 단계 실행 결과 제시 |

**사람이 한 결정 중 결과를 크게 바꾼 것 두 가지:**

1. **"각 단계 완료 시 어떻게 검증했는지 실행 가능한 명령어와 함께 제시할 것."**
   이 한 줄이 없었다면 "빌드가 통과하는 코드" 에서 멈췄을 것이다.
   아래 결함 목록의 대부분은 **실제로 실행해 봐서** 나왔다.
2. **"개선 전후 비교를 넣어라. 두 방식의 수치 차이가 이 PoC 의 핵심 근거다."**
   비교군을 제대로 만들도록 강제한 요구였고, 실제로 첫 비교군은 형편없이 느렸다(아래 참조).

## AI 가 만든 코드에서 나온 결함

전부 이 프로젝트에서 실제로 발생하고 수정된 것이다. **커밋 히스토리에 남아 있다.**

### 테스트가 잡은 것

| # | 결함 | 왜 놓쳤나 |
|---|---|---|
| 1 | **로그아웃이 동작하지 않음.** `<form method="post" action="...">` — `action` 을 직접 쓰면 `FormTagHelper` 가 안티포저리 토큰을 넣지 않는다. 토큰 없는 POST 는 400 으로 거부된다 | 화면에는 버튼이 멀쩡히 보인다. 눌러 보지 않으면 모른다 |
| 2 | **DB 경로의 커넥션 풀 고갈이 500 + 비 JSON 응답**을 냄. 테스트는 "JSON 파싱 실패" 라는 무의미한 오류만 보여줬다 | 테스트 클라이언트가 실패를 삼키고 있었다. 클라이언트를 먼저 고쳐야 진짜 원인이 보였다 |
| 3 | **앱이 DB 없이는 기동조차 못 함.** 기동 경로에서 운영자 계정을 동기로 시드하고 있었다 | 로컬에서는 DB 가 항상 먼저 떠 있다. 헬스체크 테스트를 쓰다가 드러났다 |

### 눈으로 봐서 잡은 것 — 테스트는 통과하고 있었다

| # | 결함 | 왜 테스트가 못 잡았나 |
|---|---|---|
| 4 | **감사 로그의 운영자가 `system` 으로 기록됨.** `SignInAsync` 는 응답 쿠키만 세팅하고 같은 요청의 `HttpContext.User` 는 익명 그대로다 | "로그가 남는다" 는 단언했지만 **"누가 했는지 맞게 남는다"** 는 단언하지 않았다 |
| 5 | **한글이 `&#xC774;` 로 이스케이프됨.** 기본 `HtmlEncoder` 는 비 ASCII 를 전부 숫자 참조로 바꾼다 | 브라우저는 정상 렌더한다. HTML 소스를 봐야 보인다 |
| 6 | **감사 로그 JSON 이 `신규` 로 저장됨** | 사람이 읽는 것이 존재 이유인 로그가 읽을 수 없는 상태였는데, "기록된다" 는 통과했다 |

4·6 은 **스크린샷을 눈으로 확인해서** 발견했다. 지금은 둘 다 회귀 테스트가 있다
(`log.AfterJson.Should().Contain(ev.Name).And.NotContain("\\u")`).

> **여기서 배운 것**: AI 가 작성한 테스트는 **AI 가 구현한 것과 같은 가정**을 공유한다.
> "로그를 남긴다" 를 구현하면서 "읽을 수 있게 남긴다" 를 생각하지 못했다면,
> 테스트도 그것을 검사하지 않는다. **실행 결과를 직접 보는 것이 그 공백을 메운다.**

### 측정이 잡은 것

| # | 결함 | 영향 |
|---|---|---|
| 7 | **유저 한도 조회에 인덱스가 없어 인덱스 스캔.** 그 질의에 걸린 `UPDLOCK, HOLDLOCK` 때문에 모든 트랜잭션이 25만 행에 범위 잠금을 걸고 있었다 | 비교군이 **5.6 req/s**(요청의 94% 타임아웃). 인덱스 하나로 **223 req/s (40배)** |
| 8 | **낡은 앱 인스턴스가 계속 트래픽을 받고 있었음.** 초기화 스크립트가 `ss` 로 프로세스를 찾는데, 이 환경에서 `ss` 는 아무 출력도 내지 않는다 | **그 상태의 측정치를 전부 버렸다** |

7 이 특히 중요하다. 그대로 리포트했다면 **"Redis 가 DB 보다 1,500배 빠르다"** 는
말도 안 되는 결론이 나왔을 것이다. **AI 는 자기가 만든 비교군이 형편없다는 것을 의심하지 않는다 —
수치가 이상하다고 느끼고 실행 계획을 떠본 것이 유일한 방어선이었다.**

### CI 가 잡은 것 — 로컬에서는 드러나지 않던 것

| # | 결함 | 왜 로컬에서 안 보였나 |
|---|---|---|
| 7-1 | **배포 스크립트가 생성하는 nginx 설정을 커밋**해 두어, 마지막 배포 상태(green)로 커밋된 저장소에서는 `docker compose up` 이 존재하지 않는 컨테이너를 가리켰다 | 로컬에는 직전 배포의 상태가 남아 있어 항상 앞뒤가 맞았다. **깨끗한 체크아웃**에서만 드러난다 |
| 7-2 | 프록시 컨테이너가 **root 로** 만든 설정 파일을 **일반 사용자로 도는** 배포 스크립트가 덮어쓰지 못했다 | 로컬에서는 전부 root 로 실행했다 |

전형적인 "내 머신에서는 되는데" 다. **AI 는 자기가 만든 환경에서만 확인한다** —
깨끗한 체크아웃과 다른 사용자 권한에서 매번 돌려 보는 장치가 따로 필요하다.

### 설계 단계에서 잘못 잡은 것

| # | 결함 | 수정 |
|---|---|---|
| 9 | `IssuanceLog.LatencyMs` 를 "API 처리 지연" 으로 설계했는데, 그 값은 **Lua 가 알 수 없어** 스트림에 담을 수 없다 | 실제로 의미 있는 `PersistenceLagMs`(비동기 적재 지연)로 변경 |
| 10 | `.gitignore` 없이 커밋해 **빌드 산출물 642개**가 섞여 들어감 | amend 로 정리(푸시 전) |

### 환경·인프라에서 걸린 것

`set -euo pipefail` + `grep` 조합으로 스크립트가 조용히 죽는 문제, Redis 이미지의
`ENTRYPOINT` 가 compose 의 `command` 를 덮어쓰지 못하는 문제, Redis protected-mode,
nginx upstream 중복 include, Docker vfs 드라이버의 레이어 깊이 한계 —
전부 **실제로 돌려 보기 전까지는 드러나지 않는** 것들이었다.

## 검증 방법

AI 가 "동작합니다" 라고 말하는 것은 증거가 아니다. 이 프로젝트에서 쓴 증거는 넷이다.

1. **실제 의존성 위에서 도는 통합 테스트 46건.**
   인메모리 대역이나 목이 아니라 Testcontainers 로 **진짜 MSSQL·Redis** 를 띄운다.
   동시 요청은 `TaskCompletionSource` 게이트로 전원을 출발선에 세운 뒤 한 번에 푼다 —
   그냥 `Task.WhenAll` 로 묶으면 순차적으로 출발해 경합이 거의 일어나지 않는다.

2. **실제로 띄워서 브라우저로 확인.** Playwright 로 로그인·이벤트 생성·강제 중단을 수행하고
   스크린샷을 남겼다. 결함 4·5·6 이 여기서 나왔다.

3. **k6 부하 측정.** 처리량·p50/p95/p99 를 3경로 × 3 VU 레벨로 측정하고,
   **측정 환경의 한계를 먼저 밝혔다**(부하 생성기가 대상과 같은 4코어 장비에서 돈다).

4. **CI 에서 매번 재실행.** 무중단 배포와 롤백 경로를 `deploy-smoke` 잡이 매 실행 검증한다.
   배포 중 요청 실패가 한 건이라도 나오면 잡이 실패한다.
   **깨끗한 체크아웃·다른 사용자 권한**에서 돌기 때문에 로컬에서 보이지 않던 결함이 여기서 나왔다
   (위 7-1, 7-2). 커버리지는 라인 80.6%.

## 효과가 있었던 프롬프트 패턴

### 1. 검증 방법을 결과물에 포함시키기

> "각 단계 완료 시 '어떻게 검증했는지'를 **실행 가능한 명령어와 함께** 제시할 것."

가장 효과가 컸다. "구현하라" 만 요구하면 빌드가 통과하는 코드가 나오고 거기서 멈춘다.
**검증을 결과물의 일부로 요구하면 실행할 수밖에 없고, 실행하면 결함이 드러난다.**

### 2. 코드 전에 설계안을 요구하고 승인 지점을 두기

> "먼저 프로젝트 구조와 도메인 모델을 제안하고, 내 승인을 받은 뒤 코드를 작성하라."
> "아직 코드는 작성하지 말고 설계안만 제시하라."

방향이 틀렸을 때 버리는 비용이 코드 3,000줄에서 문서 한 장으로 줄어든다.
이 프로젝트에서는 "이벤트 상태를 저장하지 않고 파생한다" 같은 결정을
**구현 전에** 합의할 수 있었다.

### 3. 트레이드오프를 먼저 설명하게 하기

> "사전 생성되거나 발급 시점에 생성된다. **둘 중 무엇이 나은지 트레이드오프를 먼저 설명하라.**"

결론만 요구하면 AI 는 가장 흔한 답을 고르고 근거를 사후에 만든다.
비교를 먼저 요구하면 선택이 실제 비교에서 나온다.

### 4. 비교 대상을 명시적으로 요구하기

> "먼저 DB 직접 차감 방식(비관적 락)으로 구현한 버전과 Redis Lua 버전을 비교 측정한다.
> **두 방식의 수치 차이가 이 PoC 의 핵심 근거다.**"

"Redis 가 빠르다" 는 주장에는 비교 대상이 필요하다.
이 요구가 없었다면 절대 수치 하나만 남았을 것이고, 그건 아무것도 증명하지 못한다.

덧붙여, 비교군을 **성실하게** 만들어야 한다는 압력도 여기서 나왔다 —
`READPAST` 변형(DB 만으로 할 수 있는 최선)을 추가한 것은
"DB 를 일부러 못 만든 것 아니냐" 는 반론을 닫기 위해서다.

### 5. 제약을 명시하기

> "별도 CSS 프레임워크 없이", "**WebSocket 도입하지 마라**", "외부 유료 서비스 의존성 없이"

제약이 없으면 AI 는 기본값으로 무거운 선택을 한다. 제약은 설계 품질을 높인다.

### 6. 진행 상황을 직접 묻기

> "이제 다 개발된거야?"

이 질문에 답하려고 실제 파일 목록을 확인했고, **6단계 중 3단계까지밖에 안 됐다**는 것과
README 가 한 줄이라는 것이 드러났다. **AI 는 방금 한 일을 과대평가하는 경향이 있다.**
중간중간 전체 진행 상황을 확인하는 질문이 교정 장치가 된다.

## 효과가 없었거나 주의가 필요했던 것

- **"10,000 VU 로 부하 테스트하라"** — 지시는 명확했지만 측정 장비가 4코어였다.
  그대로 따랐다면 대상이 아니라 부하 생성기를 측정했을 것이다.
  **지시를 그대로 따르는 것보다 왜 따를 수 없는지 설명하고 대안을 제시하는 편이 낫다**
  (200/1,000/3,000 VU 세 지점의 기울기로 대체했다).

- **AI 가 작성한 테스트만으로는 부족하다.** 결함 4·5·6 이 증거다.
  구현과 테스트가 같은 가정을 공유하면 그 가정의 공백은 검사되지 않는다.

- **AI 는 자기가 만든 비교군을 의심하지 않는다.** 결함 7 이 증거다.
  "우리 방식이 1,500배 빠르다" 같은 수치가 나오면 **먼저 자기 구현을 의심해야 한다.**
