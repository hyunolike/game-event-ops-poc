# 5단계 — CI/CD

```
브랜치 푸시 / PR  →  빌드 · 테스트 · 커버리지  →  무중단 배포 · 롤백 시연
main 머지        →  이미지 빌드 · GHCR 푸시
```

---

## 왜 Jenkins 가 아니라 GitHub Actions 인가

두 도구의 기능 차이가 아니라 **이 프로젝트가 감당할 운영 비용**의 차이로 골랐다.

| | GitHub Actions | Jenkins |
|---|---|---|
| **인프라** | 없음. 러너를 GitHub 가 준다 | 마스터 + 에이전트를 직접 띄우고 지킨다 |
| **유지보수** | 액션 버전만 관리 | 플러그인 의존성·보안 패치·디스크·JVM 튜닝이 상시 업무 |
| **코드와의 거리** | 워크플로가 저장소 안에 있고 PR 로 리뷰된다 | Jenkinsfile 도 가능하지만 잡 설정이 UI 로 새는 일이 흔하다 |
| **시크릿** | `GITHUB_TOKEN` 이 실행 단위로 발급·만료 | 크리덴셜을 직접 저장·회전해야 한다 |
| **비용** | 퍼블릭 저장소 무료, 프라이빗은 분당 과금 | 서버 비용은 고정, 사용량과 무관 |
| **빌드 환경** | 매 실행 깨끗한 러너 | 에이전트 상태가 누적된다("내 머신에선 되는데"의 서버판) |

**Actions 를 택한 이유** — 이 PoC 를 포함해 대부분의 팀에게 CI 서버 운영은 목적이 아니라 세금이다.
Jenkins 를 고르는 값은 "플러그인 생태계와 온프레미스 제어" 인데, 그 값이 필요한 조건
(폐쇄망 빌드, 특수 하드웨어, 수백 개의 레거시 잡)이 여기엔 없다.

**Jenkins 가 맞는 경우도 분명하다.** 외부망이 막힌 사내 환경, GPU·특정 OS 같은 특수 러너가 필요한 경우,
이미 수백 개의 잡이 Jenkins 에 있는 조직. 그럴 땐 이 파이프라인의 각 단계를 Jenkinsfile 로 옮기면 된다 —
빌드·테스트·이미지 푸시·헬스체크 배포라는 **단계 구성 자체는 도구와 무관하다.**

## 왜 컨테이너 배포인가

| | 컨테이너 | 서버에 직접 배포 (예: systemd + 게시물 복사) |
|---|---|---|
| 런타임 일치 | 이미지에 .NET 런타임이 들어 있다 | 서버마다 런타임 버전을 맞춰야 한다 |
| 롤백 | 이전 태그를 다시 띄우면 끝 | 이전 아티팩트를 되돌리고 의존성도 되돌려야 한다 |
| 무중단 전환 | 새 컨테이너를 띄워 놓고 트래픽만 옮긴다 | 같은 포트를 쓰는 프로세스를 교체해야 해 빈틈이 생긴다 |
| 로컬 재현 | `docker compose up` 한 줄 | 문서를 보고 손으로 맞춘다 |
| 비용 | 이미지 크기·레지스트리·빌드 시간 | 없음 |

**핵심은 롤백이다.** 배포의 가치는 "새 버전을 올리는 능력" 이 아니라 **"틀렸을 때 3분 안에 되돌리는 능력"** 에 있다.
불변 이미지는 되돌릴 대상이 명확하다 — 태그 하나다. 반면 서버에 파일을 덮어쓰는 방식은
"되돌린다" 가 무엇을 의미하는지부터 매번 달라진다.

> **쿠버네티스를 쓰지 않은 이유**: 인스턴스 한 대짜리 PoC 에 컨트롤 플레인을 얹으면
> 증명하려는 것(발급 정확성과 처리량)보다 부수 장치가 커진다.
> 다만 이 설계는 그대로 옮겨진다 — `/health/live` 는 livenessProbe, `/health/ready` 는 readinessProbe,
> blue-green 전환은 Deployment 의 롤링 업데이트에 대응한다.
> 즉 **지금 k8s 를 쓰지 않는 것이 나중에 k8s 로 가는 길을 막지 않는다.**

## 헬스체크 — 두 종류를 나눈 이유

```
GET /health/live    →  프로세스가 살아 있는가          (의존성을 보지 않는다)
GET /health/ready   →  트래픽을 받을 준비가 됐는가     (Redis·MSSQL 을 각각 확인)
GET /health         →  /health/ready 의 별칭
```

```jsonc
// 200
{ "status": "healthy",
  "checks": { "mssql": { "status": "healthy", "durationMs": 1, "error": null },
              "redis": { "status": "healthy", "durationMs": 0, "error": null } } }

// 503 — 어느 쪽이 문제인지 말해 준다
{ "status": "unhealthy",
  "checks": { "mssql": { "status": "healthy", ... },
              "redis": { "status": "unhealthy", "durationMs": 2957,
                         "error": "The message timed out in the backlog..." } } }
```

**둘을 나누지 않으면 장애가 증폭된다.** liveness 가 DB 를 확인하면, DB 가 5초 흔들릴 때
오케스트레이터가 멀쩡한 앱 인스턴스를 전부 재시작시킨다. DB 가 돌아왔을 때 맞이하는 것은
차가운 캐시와 동시 기동하는 인스턴스들이다.

구현에서 신경 쓴 것:

- **두 검사를 동시에** 돌린다. 순차로 하면 응답 시간이 합쳐져 배포 스크립트의 폴링 주기를 넘길 수 있다.
- 각 검사에 **3초 타임아웃**. 배포 스크립트 입장에서 "느린 200" 은 "빠른 503" 보다 나쁘다.
- MSSQL 검사는 `SELECT 1` 이 아니라 **실제 테이블을 건드린다**(`SELECT TOP 1 1 FROM Events`).
  `SELECT 1` 은 커넥션만 확인해서 "연결은 되는데 마이그레이션이 안 된" 상태를 통과시킨다.
- 실패 시 **원인 문자열을 함께 준다.** 원인이 비어 있으면 새벽에 호출받은 사람이 아무것도 못 한다.

### 앱이 DB 없이도 기동되어야 한다

처음에는 기동 경로에서 운영자 계정을 동기로 시드했는데, **DB 가 늦게 뜨면 앱이 아예 못 떴다.**
컨테이너 배포에서 앱이 DB 보다 먼저 기동되는 것은 예외가 아니라 일상이고, 그때마다 컨테이너가 죽으면
재시작 루프에 빠진다.

지금은 시드를 백그라운드 워커로 옮겨 **성공할 때까지 백오프하며 재시도**한다.
앱은 뜨되 `/health/ready` 가 503 을 주고, 그동안 배포 스크립트와 프록시가 트래픽을 막아 준다.
이것이 올바른 모양이다 — **"뜨지 못함" 이 아니라 "떴지만 준비되지 않음".**

## 무중단 배포 (blue-green)

`deploy/deploy.sh <이미지>` 가 하는 일:

```
1. 현재 색깔 확인 → 반대 색깔로 배포
2. 스키마 적용 (efbundle, 1회)
3. 새 인스턴스 기동
4. /health/ready 가 200 을 줄 때까지 대기        ← 전환의 게이트
5. nginx upstream 교체 + reload                  ← 전환
6. 프록시 경유 스모크 테스트
7. 옛 인스턴스 정리 (3초 유예 후)
```

**어느 단계에서 실패하든 트래픽은 옛 인스턴스에 남는다. 그것이 롤백 경로다.**
4단계에서 실패하면 전환 자체가 일어나지 않고, 6단계에서 실패하면 upstream 을 되돌린 뒤 reload 한다.

전환이 끊기지 않는 근거는 `nginx -s reload` 다 — 새 설정으로 워커를 교체하되
**기존 연결은 끊지 않고** 처리하던 요청을 마치게 한다.

### 마이그레이션을 앱에서 분리한 이유

스키마 적용은 **앱 기동이 아니라 배포 스크립트가** 한다(`efbundle`, 이미지에 포함).

앱이 기동 시 마이그레이션을 돌리면, 인스턴스를 두 개 이상 띄우는 순간 **서로 같은 스키마를
동시에 바꾸려 든다.** blue-green 은 정의상 잠깐 두 인스턴스가 공존하므로 이 문제를 반드시 만난다.
적용은 한 곳에서, 한 번만 해야 한다.

`dotnet ef migrations bundle` 로 만든 자기완결 실행 파일을 이미지에 넣었다.
배포 시점에 SDK 도 소스도 필요 없고, **이미지와 스키마 버전이 함께 움직인다.**

### 실측

로컬에서 배포하는 동안 프록시로 계속 요청을 보내며 실패를 셌다.

| 시나리오 | 결과 |
|---|---|
| 정상 배포 (blue → green) | 요청 **471건 · 실패 0건**, 준비까지 3초 |
| 실패 주입 (`--simulate-failure`) | 요청 **8,993건 · 실패 0건**, 전환 안 함, 트래픽 green 유지, 종료 코드 1 |

실패 주입은 새 인스턴스에 닿을 수 없는 Redis 를 주어 준비 상태가 되지 못하게 한 것이다.
배포 스크립트는 90초를 기다린 뒤 전환을 포기하고 새 컨테이너를 제거했다.
**그동안 서비스는 한 건도 실패하지 않았다.**

이 두 시나리오는 CI 의 `deploy-smoke` 잡에서도 매번 돌아간다 —
실패가 한 건이라도 나오면 잡이 실패한다. "무중단" 을 주장하려면 그것을 측정해야 한다.

## 파이프라인 구성

### `ci.yml` — PR · 브랜치 푸시

| 단계 | 하는 일 |
|---|---|
| 복원 | NuGet 캐시 적중 시 대부분 생략 |
| 빌드 | Release 구성 |
| 테스트 | **Testcontainers 로 실제 MSSQL·Redis** 를 띄워 통합 테스트 44건 |
| 커버리지 | cobertura 수집 → ReportGenerator → **실행 요약에 직접 표시** |
| 아티팩트 | trx + HTML 리포트 (14일 보관) |
| 배포 시연 | compose 기동 → 무중단 배포 → **롤백 경로 확인** |

커버리지를 아티팩트로만 남기지 않고 실행 요약에 띄우는 이유는 단순하다 —
**아티팩트는 아무도 다운로드하지 않는다.**

### `release.yml` — main 머지

이미지를 빌드해 GHCR 에 푸시한다. 태그는 `sha-<커밋>` 과 `latest`.
실행 요약에 **그 이미지로 배포하는 명령**을 그대로 찍어 준다.

`GITHUB_TOKEN` 으로 로그인하므로 별도 시크릿이 없고, 토큰이 실행 단위로 만료된다.
권한은 `packages: write` 하나만 준다.

## 빌드 이미지에서 신경 쓴 것

- **멀티스테이지**: SDK 는 빌드에만 쓰고 런타임 이미지에는 게시물만 남긴다 (최종 **270MB**).
- **레이어 순서**: `.csproj` 만 먼저 복사해 `restore` → 소스만 바뀌면 복원 레이어가 캐시된다.
- **비 root 실행**: .NET 8 이미지가 제공하는 `app` 사용자(UID 1654).
- **curl·wget 을 넣지 않는다**: 컨테이너 HEALTHCHECK 는 앱 자신이 한다
  (`dotnet CouponOps.Web.dll --healthcheck`). 패키지를 추가하면 이미지가 커지고
  **빌드가 외부 apt 저장소에 의존**하게 된다 — 폐쇄망에서 빌드가 막히는 흔한 원인이다.
  대가는 검사마다 .NET 프로세스가 하나 뜨는 것인데, 10초 간격이면 무시할 만하다.
- **사설 CA 훅**: `certs/` 에 `.crt` 를 넣으면 빌드 단계 신뢰 목록에 추가된다.
  비어 있으면 무동작이므로 일반 환경에서는 신경 쓸 필요가 없다.

## 남은 과제

- **배포 대상이 로컬 한 대다.** 실제 서버로 나가려면 SSH 또는 오케스트레이터 연동이 필요하다.
  이 PoC 는 "전환과 롤백이 헬스체크로 게이트된다" 까지를 보인다.
- **DB 마이그레이션 롤백은 다루지 않는다.** 앱은 이전 이미지로 되돌릴 수 있지만 스키마는 아니다.
  실무에서는 하위 호환 마이그레이션(확장 후 수축) 규칙이 함께 필요하다.
- **시크릿이 compose 에 평문으로 있다.** 로컬 개발 기본값이며, 실제 배포에서는
  시크릿 저장소에서 주입해야 한다.
